# Агентный RAG

## Зачем нужен агентный RAG

В стандартном RAG каждое сообщение пользователя вызывает ровно **один** поиск. Система ищет, формирует контекст и генерирует ответ — независимо от ситуации. Это работает для простых вопросов, но не справляется, когда:

- Вопрос требует **нескольких поисков** по разным темам (например, «Сравни политику возврата для оборудования и программного обеспечения»)
- Первый результат поиска **недостаточен** и система должна уточнить запрос и повторить попытку
- Некоторые вопросы **вообще не требуют поиска** (например, «Подведи итог нашего разговора»)
- Ответ зависит от сочетания **поиска по документам с актуальными данными** из API

Агентный RAG решает все эти задачи. Вместо фиксированного пайплайна «извлечь → ответить» **агент решает самостоятельно** — когда искать, что именно искать, стоит ли искать повторно и когда вызывать другие инструменты — всё это внутри цикла ReAct.

## Быстрый старт

Зарегистрируйте `RagStore` как инструмент через `WithAgenticRag`, затем запустите `RunAgentAsync`:

```csharp
// Строим индекс один раз
var ragStore = await RagStore.BuildAsync(cfg => cfg
    .AddDocument("manual.pdf")
    .AddDocument("policy.docx")
    .UseOpenAIEmbedding(apiKey));

// Регистрируем RAG как инструмент и запускаем агента
var service = new AnthropicService(apiKey, http);
service.WithAgenticRag(ragStore);

var answer = await service.RunAgentAsync("Summarise the refund policy.");
```

Агент автоматически вызывает `search_documents`, когда ему нужен контекст из документов, а затем синтезирует финальный ответ из полученных фрагментов.

## Сочетание с другими инструментами

Агентный RAG особенно хорош в сочетании с дополнительными инструментами — агент выбирает нужный инструмент для каждой подзадачи:

```csharp
var service = new AnthropicService(apiKey, http);

service.WithAgenticRag(ragStore)
       .WithFunctionAsync("get_order_status", "Look up an order status by order ID.",
           ("order_id", "The order ID to look up.", required: true),
           async id => await orderApi.GetStatusAsync(id));

// Агент ищет в документах политику И вызывает API для получения данных заказа
var answer = await service.RunAgentAsync(
    "Order #12345 — am I eligible for a refund based on the current policy?");
```

В этом примере агент автоматически:

1. Ищет в документах политику возврата
2. Вызывает API заказов для получения статуса заказа #12345
3. Объединяет обе части информации для формирования итогового ответа

## Настройка описания инструмента

Описание инструмента определяет, когда агент решает использовать RAG. Адаптируйте его под вашу предметную область для более точного выбора инструмента:

```csharp
service.WithAgenticRag(ragStore,
    toolDescription:
        "Search internal HR policies, product manuals, and compliance documents. " +
        "Call this tool whenever company-specific policy or product information is needed.");
```

Расплывчатое описание типа «Search documents» может привести к слишком частому или, наоборот, слишком редкому вызову RAG. Указывайте конкретно, **какого рода информация** содержится в документах.

## Отличия от стандартного RAG

| | Стандартный RAG | Агентный RAG |
| --- | --- | --- |
| Момент поиска | Каждое сообщение | Решает агент |
| Формулировка запроса | QueryRewriter | Сам агент |
| Количество поисков | Один за ход | Один или несколько по необходимости |
| Комбинация инструментов | Не применимо | Любой зарегистрированный инструмент |
| Подключение | `.WithRag()` | `.WithAgenticRag()` + `RunAgentAsync` |

> **Примечание:** `QueryRewriter` намеренно не используется в агентном RAG. Агент сам формулирует самодостаточный поисковый запрос, поэтому отдельный этап переписывания был бы избыточен и мог бы исказить намерение агента.

## Когда выбирать какой вариант

- **Стандартный RAG** — каждый вопрос связан с документами, касается одной темы, и важна минимальная задержка
- **Агентный RAG** — вопросы охватывают несколько тем, требуют сочетания документов и актуальных данных или нуждаются в итеративном извлечении
