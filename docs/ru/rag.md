# RAG (генерация с извлечением)

Для готового ответа и кнопки Стоп передайте `cancellationToken` в `GetCompletionAsync`. Run нужен для событий прогресса или поддерживаемых дополнительных указаний. См. [отмену ответа](completions.md#completion-cancellation).

Для ответа с найденным контекстом также передавайте `cancellationToken` в `RagEnabledService.GetCompletionAsync`. Он проходит через поиск, `LlmQueryRewriter`, `LlmReranker` и внутренний запрос; отмена при поиске предотвращает следующий вызов модели. `RagPipeline.QueryAndGenerateAsync` также передаёт токен. Компоненты должны поддерживать отмену; завершённые поиски и действия инструментов не откатываются.

После поиска документов подготовка ответа может занять время. [Run](execution-api-transition.md) позволяет показывать её ход и отменять выполнение, сохраняя RAG-поиск и дополнение контекста.


Для ссылки `IAIService` используйте `GetLastProcessing()` из `Mythosia.AI.Extensions`. Метод читает необязательный `IAIProcessingInfoService` и возвращает пустой список, если диагностика недоступна. Обязательных членов в `IAIService` не добавляется. В RAG `RagEnabledService.WithSpeed(...)` настраивает следующий ответ после поиска, а `LastProcessing` описывает этот ответ. Внутреннее переписывание отделено; Run предоставляет те же записи `Processing`. [WithSpeed](request-building.md#inference-speed)

## Что такое RAG

RAG (Retrieval-Augmented Generation) — технология, при которой AI-модель сначала **находит релевантную информацию в ваших документах**, а затем формирует ответ на её основе.

Представьте, что вы пишете реферат в библиотеке. Вместо того чтобы полагаться только на память, вы сначала находите нужные книги и используете их как опору. Именно так работает RAG.

## Зачем нужен RAG

LLM отвечает на основе обучающих данных, а значит:

- **Не знает свежую информацию** — данные после обучения ему недоступны
- **Не знает внутренних документов** — корпоративные политики и мануалы ему не видны
- **Галлюцинации** — может уверенно выдумывать факты

RAG решает эти проблемы: при поступлении вопроса сначала выполняется поиск по вашим документам, а результаты добавляются в промпт, чтобы модель генерировала **обоснованный ответ**.

## Поток работы RAG

### 1. Подготовка документов (выполняется один раз)

```
Файлы → Разбиение на чанки → Эмбеддинг (векторизация) → Сохранение в векторное хранилище
```

### 2. Ответ на вопрос (при каждом запросе)

Ниже показан стандартный векторный режим. Лексический режим пропускает эмбеддинг запроса, а собственный поисковый компонент выбирает нужную подготовку.

```
Вопрос → Эмбеддинг вопроса → Поиск похожих чанков → Добавление в промпт → Генерация ответа
```

## Установка

```bash
dotnet add package Mythosia.AI.Rag
```

## Быстрый старт

В Mythosia.AI весь процесс настраивается одной строкой `.WithRag()`:

```csharp
using Mythosia.AI.Rag;

var service = new AnthropicService(apiKey, http)
    .WithRag(rag => rag
        .AddDocument("manual.txt")
        .AddDocument("policy.txt")
    );

var response = await service.GetCompletionAsync("Какова политика возврата?");
```

Необязательная предварительная версия `Mythosia.AI.Rag.Search.Pixie` позволяет сравнить локальный нейронный разреженный поиск с существующим. Она сохраняет поставщика плотных эмбеддингов и хранит индекс PIXIE в памяти, не переносит постоянные хранилища и не заменяет стандартный поиск. [Настройка PIXIE и сравнение (английский)](rag-hybrid-search.md#pixie-search).

<a id="rag-message-attachments"></a>

## Ответ о вложении с опорой на ваши документы

Чтобы объяснить фотографию товара с опорой на руководство, передайте `Message` с вопросом и изображением в `RagEnabledService.GetCompletionAsync(Message)` или `StartRunAsync(Message)`. Оба метода сохраняют нетекстовые вложения в запросе к внутреннему сервису ИИ. Поиск использует текст сообщения; сами вложения не индексируются и не преобразуются в эмбеддинги автоматически. Выбранные поставщик и модель должны поддерживать этот тип вложения. Найденный контекст добавляется только в отправляемый запрос: он не перезаписывает исходный `Message` и не заменяет текст пользователя в истории разговора.

Если для ответа нужны и руководство, и актуальные остатки на складе, сочетайте RAG с зарегистрированными инструментами. Во время вызовов инструментов через `GetCompletionAsync` найденный контекст остаётся в исходном вводе, а каждый последующий результат инструмента передаётся модели без изменений. История сохраняет исходный ввод пользователя.

<a id="retrieval-modes"></a>

## Выбор способа поиска документов

Коды товаров удобно искать по словам, а вопросы с другой формулировкой — по смыслу. Выбранный компонент готовит только нужное представление: лексический поиск больше не требует предварительного эмбеддинга запроса.

```csharp
RagStore store = await RagStore.BuildAsync(rag => rag
    .AddDocument("manual.txt")
    .UseKeywordSearch());

RagProcessedQuery result = await store.QueryAsync("refund policy");
```

`UseKeywordSearch()` пропускает эмбеддинг запроса. При загрузке документы по-прежнему разбиваются и векторизуются для существующего хранилища; это не чисто текстовая индексация. При отложенной инициализации первая операция может вызвать эмбеддинги документов.

См. [режимы и поддержку хранилищ](rag-hybrid-search.md) и [собственные компоненты поиска](rag-pipeline.md#custom-retriever).

## Добавление документов

```csharp
.WithRag(rag => rag
    .AddDocument("readme.txt")                    // Локальный файл
    .AddUrl("https://example.com/doc.txt")        // URL
    .AddText("Инлайн-контент.")                   // Строка напрямую
)
```

`AddUrl` проверяет и распаковывает поддерживаемое HTTP-сжатие перед чтением текста и отклоняет неполные, неподдерживаемые или многослойные кодировки. См. [распаковка URL-документов и отмена](rag-pipeline.md#url-documents).

<a id="document-identity"></a>

### Как различать файлы с одинаковым именем

Две компании могут предоставить по файлу `docs/faq.txt`. Оба документа должны остаться в индексе, а повторная регистрация того же файла — использовать прежний идентификатор:

```csharp
var store = await RagStore.BuildAsync(rag => rag
    .AddDocuments("company-a/docs")
    .AddDocuments("company-b/docs"));
```

В стандартном процессе хранения RAG идентификатор документа создаётся до отправки записей в векторное хранилище, после чего записи с совпадающим `document_id` заменяются. Наше хранилище PostgreSQL (pgvector) использует этот ID и не проверяет исходный путь файла самостоятельно. Раньше при регистрации каталогов для `company-a/docs/faq.txt` и `company-b/docs/faq.txt` отправлялся один и тот же ID — `faq.txt`, поэтому второй документ заменял первый. Исправление сохраняет полный путь при создании ID; схема PostgreSQL не меняется. Фильтр `full_path` в примере хранения использует метаданные, переданные вызывающим кодом, и не создаёт автоматически уникальные ID документов или записей.

Встроенные `PlainTextDocumentLoader` и `DirectoryDocumentLoader` используют абсолютный путь файла, нормализованный через `Path.GetFullPath`, как `Source` и автоматический ID документа. Поэтому файлы из разных каталогов получают разные ID. Относительный, абсолютный и содержащий `./` путь дают один ID, если разрешаются в одинаковый абсолютный путь с учётом регистра. Для относительных путей сохраняйте рабочий каталог неизменным. Перемещение файлов, символические или жёсткие ссылки и другой регистр не гарантируют сохранения ID.

`AddText(..., id: ...)`, явно заданный `RagDocument.Id` и правила `Source` пользовательских загрузчиков не меняются. Менять API вызова не требуется. Поскольку `Source` этих встроенных загрузчиков теперь абсолютный, стандартные ссылки на источники тоже могут показывать абсолютный путь. Для отображения используйте `filename` или метаданные `relative_path` стандартного загрузчика каталогов. Перегрузка регистрации каталога с настройками не добавляет `relative_path` автоматически.

**Существующие индексы:** Старые относительные ID не удаляются и не мигрируют автоматически. Предпочтительно заново проиндексировать все документы в новой коллекции, проверить её и затем переключить приложение. Если используется прежняя коллекция, удаляйте только старые ID, принадлежность которых проверена, и повторно индексируйте их исходные файлы. Не удаляйте документы массово по имени файла: в других каталогах могут быть документы с тем же именем.

Чтобы обновление и удаление затрагивали только нужный документ, `document_id` зарезервирован конвейером. Перед сохранением каждая запись получает фактический `RagDocument.Id`, даже если входные метаданные содержат другое значение. Словари метаданных исходного документа и разделителя не изменяются; пользовательские обработчики сохранения также получают нормализованные записи. Для идентификатора приложения используйте другой ключ.

Это не исправляет записи, уже сохранённые с неверным `document_id`. Создайте новую коллекцию из проверенных исходных документов либо установите принадлежность и очистите только затронутые записи перед переиндексацией. Повторная индексация с правильным ID сама по себе не позволяет надёжно найти старые записи под другим ID.

Один файл, зарегистрированный по относительному и абсолютному пути, должен обновлять один документ, а одноимённые файлы в разных папках должны оставаться разными. `WordDocumentLoader`, `ExcelDocumentLoader`, `PowerPointDocumentLoader` и `PdfDocumentLoader` теперь записывают в `DoclingDocument.Source` нормализованный абсолютный путь, как встроенные TXT-загрузчики. RAG строит по нему автоматический ID; явно заданные ID остаются под контролем вызывающего кода. В стандартных ссылках на источники могут отображаться абсолютные пути.

[Сохранять стабильную идентичность файла](document-loaders.md#file-source-identity).

<a id="empty-document-updates"></a>

### Очистка документа без сохранения устаревших результатов

Если вы очистили отменённые правила возврата и повторно индексируете тот же документ, старый текст больше не должен попадать в ответы. При стандартном хранении RAG успешное разбиение с нулевым количеством фрагментов заменяет записи соответствующего `document_id` пустым набором. Эмбеддинги не запрашиваются, записи других документов сохраняются. Это относится к пустым документам и документам из пробелов, если их разбиение даёт ноль фрагментов, а также к пользовательским разделителям, успешно возвращающим ноль фрагментов.

Для уже настроенного экземпляра `RagPipeline` с именем `pipeline` используйте сохранённый ID документа:

```csharp
await pipeline.IndexDocumentAsync(
    new RagDocument { Id = "refund-policy", Content = "" },
    cancellationToken);
```

Позже можно снова индексировать непустой текст с тем же ID. Отсутствие документов в результате загрузчика или отсутствие документа в последующем списке файлов не означает команду удаления: ID для замены не был передан.

Исключения при загрузке, разборе или разбиении, а также отмена, обнаруженная до вызова хранилища, сохраняют прежние записи этого документа. Загрузчики и парсеры должны сообщать об ошибках исключениями: успешный результат из нуля фрагментов нельзя отличить от намеренной очистки. После начала записи откат при ошибке или отмене зависит от хранилища; PostgreSQL выполняет замену в транзакции. Пакет обрабатывается по документам и не откатывает ранее завершённые документы.

**Собственное хранение:** при передаче `onDocumentEmbedded` сохранением по-прежнему управляет этот callback. При нуле фрагментов он не вызывается и стандартное хранилище не используется. Приложение должно явно удалить известный ID в своём хранилище либо вызвать `DeleteDocumentAsync` для хранилища конвейера.

## Свой провайдер эмбеддингов

```csharp
using Mythosia.AI.Rag.Embeddings;

var embedder = new OpenAIEmbeddingProvider(apiKey, http, "text-embedding-3-small");

var service = new AnthropicService(apiKey, http)
    .WithRag(rag => rag
        .UseEmbedding(embedder)
        .AddDocument("knowledge-base.txt")
    );
```

## Свое векторное хранилище

По умолчанию используется in-memory хранилище. Для продакшена подключите постоянное:

```bash
dotnet add package Mythosia.VectorDb.Postgres
```

```csharp
using Mythosia.VectorDb.Postgres;

var store = new PostgresStore(new PostgresOptions
{
    ConnectionString = connectionString,
    Dimension = 1536
});

var service = new OpenAIService(apiKey, http)
    .WithRag(rag => rag
        .UseStore(store)
        .AddDocument("large-corpus.txt")
    );
```

## Параметры запроса

```csharp
var options = new RagQueryOptions
{
    FinalFilter = new RagFilter
    {
        TopK = 5,
        MinScore = 0.7
    }
};

var response = await service.GetCompletionAsync("Вопрос", options: options);
```

Если индекс уже размещён у провайдера модели, сравните RAG с [нативным файловым поиском и общими параметрами рассуждения](reasoning-and-search.md).
