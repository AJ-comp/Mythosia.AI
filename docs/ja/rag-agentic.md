# エージェンティックRAG

## 標準RAGの限界

標準RAGはシンプルで高速です。質問が来ると必ず**1回**検索し、結果をプロンプトに入れて回答を生成します。しかし、この「必ず1回」という方式は複雑な状況で限界が見えてきます：

- **「ハードウェアとソフトウェアの返金ポリシーを比較してください」** → 1回の検索では2つのトピックを十分にカバーできません
- **最初の検索結果が不十分なとき** → 標準RAGはリトライせず、不足した結果のまま回答します
- **「今までの会話を要約してください」** → ドキュメント検索がまったく不要な質問なのに検索を実行してしまいます
- **ドキュメント＋リアルタイムデータが同時に必要なとき** → 標準RAGはドキュメント検索しかできず、API呼び出しなどは対応できません

## エージェンティックRAGとは？

エージェンティックRAGはこれらの限界を解決します。固定された「検索 → 回答」パイプラインの代わりに、**AIエージェントが自ら判断**します：

- いまドキュメント検索が必要か？
- 何を検索すべきか？
- 検索結果は十分か、もう一度検索すべきか？
- ドキュメント検索の代わりに別のTool（API呼び出しなど）を使うべきか？

これらの判断がすべて**ReActループ**の中で自動的に行われます。人が図書館で資料を探すとき「この本だけでは足りないから別の棚も探そう」と自分で判断するのと似ています。

## クイックスタート

`WithAgenticRag`でドキュメントインデックスをToolとして登録し、`RunAgentAsync`でエージェントを実行します：

```csharp
// インデックスを一度だけビルド
var ragStore = await RagStore.BuildAsync(cfg => cfg
    .AddDocument("manual.pdf")
    .AddDocument("policy.docx")
    .UseOpenAIEmbedding(apiKey));

// RAGをToolとして登録してエージェントを実行
var service = new AnthropicService(apiKey, http);
service.WithAgenticRag(ragStore);

var answer = await service.RunAgentAsync("返金ポリシーを要約してください。");
```

エージェントはドキュメントが必要だと判断すると自動的に`search_documents`を呼び出し、検索された内容をもとに最終的な回答を生成します。

## 他のToolとの組み合わせ

エージェンティックRAGの本当の強みは、**ドキュメント検索と他のToolを一緒に使える**点です。エージェントが質問の各部分に必要なToolを自ら選んで使います：

```csharp
var service = new AnthropicService(apiKey, http);

service.WithAgenticRag(ragStore)
       .WithFunctionAsync("get_order_status", "注文IDで注文ステータスを照会します。",
           ("order_id", "照会する注文ID。", required: true),
           async id => await orderApi.GetStatusAsync(id));

// エージェントがポリシーはドキュメントから検索し、注文状況はAPIから取得
var answer = await service.RunAgentAsync(
    "注文 #12345 — 現在のポリシーで返金対象ですか？");
```

上記の例では、エージェントが自律的に以下のプロセスを実行します：

1. ドキュメントから返金ポリシーを検索
2. 注文APIを呼び出して注文 #12345のステータスを取得
3. 両方の情報を総合して最終回答を生成

## Toolの説明をカスタマイズ

エージェントはToolの説明（description）を見て「この状況でこのToolを使うべきか？」を判断します。そのため、Tool説明をドメインに合わせて具体的に書くことが重要です：

```csharp
service.WithAgenticRag(ragStore,
    toolDescription:
        "社内HRポリシー、製品マニュアル、コンプライアンス文書を検索します。" +
        "会社のポリシーや製品に関する情報が必要なときに呼び出してください。");
```

「ドキュメントを検索」のようにあいまいに書くと、エージェントがRAGを呼び出しすぎたり、十分に呼び出さなかったりする原因になります。ドキュメントに**どのような種類の情報**が含まれているかを具体的に記述しましょう。

## 標準RAGとの比較

| | 標準RAG | エージェンティックRAG |
| --- | --- | --- |
| 検索タイミング | メッセージごとに必ず実行 | エージェントが必要なときだけ |
| クエリ生成 | QueryRewriterが処理 | エージェントが直接生成 |
| 検索回数 | ターンごとに1回固定 | 必要に応じて複数回 |
| Toolの組み合わせ | ドキュメント検索のみ | API呼び出しなど他のToolと自由に組み合わせ |
| 設定方法 | `.WithRag()` | `.WithAgenticRag()` + `RunAgentAsync` |

> **注意：** エージェンティックRAGでは`QueryRewriter`は意図的に使用されません。エージェントが自ら独立した検索クエリを作るため、別途の書き換えステップは不要であり、むしろエージェントの意図を歪める可能性があります。

## どちらを選ぶべきか？

- **標準RAG** — すべての質問がドキュメントベースで、1つのトピックに関する質問で、素早い応答が重要な場合
- **エージェンティックRAG** — 質問が複数トピックにまたがる場合、ドキュメント＋リアルタイムデータを併用する場合、状況に応じて柔軟な検索が必要な場合
