# Агентний RAG

## Навіщо потрібен агентний RAG

У стандартному RAG кожне повідомлення користувача запускає рівно **один** пошук. Система шукає, формує контекст і генерує відповідь — незалежно від ситуації. Це працює для простих запитань, але не справляється, коли:

- Запитання потребує **кількох пошуків** за різними темами (наприклад, «Порівняй політику повернення для обладнання та програмного забезпечення»)
- Перший результат пошуку **недостатній** і система має уточнити запит та спробувати знову
- Деякі запитання **взагалі не потребують пошуку** (наприклад, «Підсумуй нашу розмову»)
- Відповідь залежить від поєднання **пошуку по документах з актуальними даними** з API

Агентний RAG вирішує всі ці завдання. Замість фіксованого пайплайну «витягти → відповісти» **агент вирішує самостійно** — коли шукати, що саме шукати, чи варто шукати повторно і коли викликати інші інструменти — все це всередині циклу ReAct.

## Швидкий старт

Зареєструйте `RagStore` як інструмент через `WithAgenticRag`, потім запустіть `RunAgentAsync`:

```csharp
// Будуємо індекс один раз
var ragStore = await RagStore.BuildAsync(cfg => cfg
    .AddDocument("manual.pdf")
    .AddDocument("policy.docx")
    .UseOpenAIEmbedding(apiKey));

// Реєструємо RAG як інструмент та запускаємо агента
var service = new AnthropicService(apiKey, http);
service.WithAgenticRag(ragStore);

var answer = await service.RunAgentAsync("Summarise the refund policy.");
```

Агент автоматично викликає `search_documents`, коли йому потрібен контекст із документів, а потім синтезує фінальну відповідь із отриманих фрагментів.

## Поєднання з іншими інструментами

Агентний RAG особливо добрий у поєднанні з додатковими інструментами — агент обирає потрібний інструмент для кожного підзавдання:

```csharp
var service = new AnthropicService(apiKey, http);

service.WithAgenticRag(ragStore)
       .WithFunctionAsync("get_order_status", "Look up an order status by order ID.",
           ("order_id", "The order ID to look up.", required: true),
           async id => await orderApi.GetStatusAsync(id));

// Агент шукає в документах політику І викликає API для отримання даних замовлення
var answer = await service.RunAgentAsync(
    "Order #12345 — am I eligible for a refund based on the current policy?");
```

У цьому прикладі агент автоматично:

1. Шукає в документах політику повернення
2. Викликає API замовлень для отримання статусу замовлення #12345
3. Поєднує обидві частини інформації для формування підсумкової відповіді

## Налаштування опису інструмента

Опис інструмента визначає, коли агент вирішує використати RAG. Адаптуйте його під вашу предметну область для точнішого вибору інструмента:

```csharp
service.WithAgenticRag(ragStore,
    toolDescription:
        "Search internal HR policies, product manuals, and compliance documents. " +
        "Call this tool whenever company-specific policy or product information is needed.");
```

Розмитий опис на кшталт «Search documents» може призвести до надто частого або, навпаки, надто рідкого виклику RAG. Вказуйте конкретно, **якого роду інформація** міститься в документах.

## Відмінності від стандартного RAG

| | Стандартний RAG | Агентний RAG |
| --- | --- | --- |
| Момент пошуку | Кожне повідомлення | Вирішує агент |
| Формулювання запиту | QueryRewriter | Сам агент |
| Кількість пошуків | Один за хід | Один або кілька за потребою |
| Комбінація інструментів | Не застосовно | Будь-який зареєстрований інструмент |
| Підключення | `.WithRag()` | `.WithAgenticRag()` + `RunAgentAsync` |

> **Примітка:** `QueryRewriter` навмисно не використовується в агентному RAG. Агент сам формулює самодостатній пошуковий запит, тому окремий етап переписування був би зайвим і міг би спотворити намір агента.

## Коли обирати який варіант

- **Стандартний RAG** — кожне запитання пов'язане з документами, стосується однієї теми, і важлива мінімальна затримка
- **Агентний RAG** — запитання охоплюють кілька тем, потребують поєднання документів та актуальних даних або потребують ітеративного витягування
