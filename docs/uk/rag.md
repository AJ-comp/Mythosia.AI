# RAG (генерація з витягуванням)

Для готової відповіді й кнопки Стоп передайте `cancellationToken` у `GetCompletionAsync`. Run потрібен для подій прогресу або підтримуваних додаткових вказівок. Див. [скасування відповіді](completions.md#completion-cancellation).

Для відповіді зі знайденим контекстом також передавайте `cancellationToken` у `RagEnabledService.GetCompletionAsync`. Він проходить через пошук, `LlmQueryRewriter`, `LlmReranker` і внутрішній запит; скасування під час пошуку запобігає наступному виклику моделі. `RagPipeline.QueryAndGenerateAsync` також передає токен. Компоненти мають підтримувати скасування; завершені пошуки й дії інструментів не відкочуються.


Для посилання `IAIService` використовуйте `GetLastProcessing()` із `Mythosia.AI.Extensions`. Метод читає необов’язковий `IAIProcessingInfoService` і повертає порожній список, якщо діагностика недоступна. Обов’язкових членів до `IAIService` не додається. У RAG `RagEnabledService.WithSpeed(...)` налаштовує наступну відповідь після пошуку, а `LastProcessing` описує її. Внутрішнє переписування відокремлено; Run надає ті самі записи `Processing`. [WithSpeed](request-building.md#inference-speed)

## Що таке RAG

RAG (Retrieval-Augmented Generation) — технологія, при якій AI-модель спочатку **знаходить релевантну інформацію у ваших документах**, а потім формує відповідь на її основі.

Уявіть, що ви пишете реферат у бібліотеці. Замість того щоб покладатися лише на пам'ять, ви спочатку знаходите потрібні книги і використовуєте їх як опору. Саме так працює RAG.

## Навіщо потрібен RAG

LLM відповідає на основі навчальних даних, а отже:

- **Не знає свіжу інформацію** — дані після навчання йому недоступні
- **Не знає внутрішніх документів** — корпоративні політики й мануали йому не видні
- **Галюцинації** — може впевнено вигадувати факти

RAG вирішує ці проблеми: при надходженні запитання спочатку виконується пошук по ваших документах, а результати додаються до промпту, щоб модель генерувала **обґрунтовану відповідь**.

Якщо провайдер уже керує індексом документів, порівняйте [розміщений пошук файлів і RAG](reasoning-and-search.md). Посилання пошуку RAG та джерела, повернуті провайдером, зберігаються окремо.

## Потік роботи RAG

### 1. Підготовка документів (виконується один раз)

```
Файли → Розбиття на чанки → Ембеддинг (векторизація) → Збереження у векторне сховище
```

### 2. Відповідь на запитання (при кожному запиті)

Нижче показано стандартний векторний режим. Лексичний режим пропускає ембеддинг запиту, а власний пошуковий компонент обирає потрібну підготовку.

```
Запитання → Ембеддинг запитання → Пошук схожих чанків → Додавання до промпту → Генерація відповіді
```

## Встановлення

```bash
dotnet add package Mythosia.AI.Rag
```

## Швидкий старт

Використовуйте `.WithRag()` на будь-якому `IAIService` для увімкнення RAG з fluent API:

```csharp
using Mythosia.AI.Rag;

var service = new AnthropicService(apiKey, http)
    .WithRag(rag => rag
        .AddDocument("manual.txt")
        .AddDocument("policy.txt")
    );

var response = await service.GetCompletionAsync("What is the refund policy?");
```

Документи автоматично розбиваються, ембеддяться та зберігаються. При запиті найбільш релевантні чанки витягуються й додаються до промпту.

Необов’язкова попередня версія `Mythosia.AI.Rag.Search.Pixie` дає змогу порівняти локальний нейронний розріджений пошук із наявним. Вона зберігає постачальника щільних ембедингів та індекс PIXIE у пам’яті, не переносить постійні сховища й не замінює типовий пошук. [Налаштування PIXIE та порівняння (англійською)](rag-hybrid-search.md#pixie-search).

## Відповідь про вкладення на основі ваших документів

Щоб пояснити фотографію товару на основі посібника, передайте `Message` із запитанням і зображенням до `RagEnabledService.GetCompletionAsync(Message)` або `StartRunAsync(Message)`. Обидва методи зберігають нетекстові вкладення в запиті до внутрішнього сервісу ШІ. Пошук використовує текст повідомлення; самі вкладення не індексуються та не перетворюються на ембединги автоматично. Вибрані постачальник і модель мають підтримувати цей тип вкладення. Знайдений контекст додається лише до запиту, що надсилається: він не перезаписує початковий `Message` і не замінює текст користувача в історії розмови.

Якщо для відповіді потрібні і посібник, і поточні складські залишки, поєднайте RAG із зареєстрованими інструментами. Під час викликів інструментів через `GetCompletionAsync` знайдений контекст залишається в початковому вводі, а кожен наступний результат інструмента передається моделі без змін. Історія зберігає початковий ввід користувача.

## Вибір способу пошуку документів

Коди товарів зручно шукати за словами, а питання з іншим формулюванням — за змістом. Вибраний компонент готує лише потрібне представлення: лексичний пошук більше не вимагає попереднього ембеддингу запиту.

```csharp
RagStore store = await RagStore.BuildAsync(rag => rag
    .AddDocument("manual.txt")
    .UseKeywordSearch());

RagProcessedQuery result = await store.QueryAsync("refund policy");
```

`UseKeywordSearch()` пропускає ембеддинг запиту. Документи досі розбиваються і векторизуються для наявного сховища; це не суто текстове індексування. Відкладена ініціалізація може викликати ембеддинги документів під час першого питання.

Див. [режими та підтримку](rag-hybrid-search.md) і [власні пошукові компоненти](rag-pipeline.md#custom-retriever).

## Додавання документів

Підтримується кілька типів джерел:

```csharp
.WithRag(rag => rag
    .AddDocument("readme.txt")                    // локальний файл
    .AddUrl("https://example.com/doc.txt")        // URL
    .AddText("Inline content can go here too.")   // текст напряму
)
```

`AddUrl` перевіряє та розпаковує підтримуване HTTP-стиснення перед читанням тексту й відхиляє неповні, непідтримувані або багатошарові кодування. Див. [розпакування URL-документів і скасування](rag-pipeline.md#url-documents).

<a id="document-identity"></a>

### Як розрізняти файли з однаковою назвою

Дві компанії можуть надати по файлу `docs/faq.txt`. Обидва документи мають залишитися в індексі, а повторна реєстрація того самого файлу — використовувати попередній ідентифікатор:

```csharp
var store = await RagStore.BuildAsync(rag => rag
    .AddDocuments("company-a/docs")
    .AddDocuments("company-b/docs"));
```

У стандартному процесі зберігання RAG ідентифікатор документа створюється перед надсиланням записів до векторного сховища, після чого записи з відповідним `document_id` замінюються. Наше сховище PostgreSQL (pgvector) використовує цей ID і не перевіряє початковий шлях файлу самостійно. Раніше під час реєстрації каталогів для `company-a/docs/faq.txt` і `company-b/docs/faq.txt` надсилався однаковий ID — `faq.txt`, тому другий документ замінював перший. Виправлення зберігає повний шлях під час створення ID; схема PostgreSQL не змінюється. Фільтр `full_path` у прикладі зберігання використовує метадані, передані кодом виклику, і не створює автоматично унікальні ID документів або записів.

Вбудовані `PlainTextDocumentLoader` і `DirectoryDocumentLoader` використовують абсолютний шлях файлу, нормалізований через `Path.GetFullPath`, як `Source` та автоматичний ID документа. Тому файли з різних каталогів отримують різні ID. Відносний, абсолютний і такий, що містить `./`, шлях дають один ID, якщо перетворюються на однаковий абсолютний шлях з урахуванням регістру. Для відносних шляхів зберігайте робочий каталог незмінним. Переміщення файлів, символічні або жорсткі посилання та інший регістр не гарантують збереження ID.

`AddText(..., id: ...)`, явно заданий `RagDocument.Id` і правила `Source` власних завантажувачів не змінюються. Змінювати API виклику не потрібно. Оскільки `Source` цих вбудованих завантажувачів тепер абсолютний, стандартні посилання на джерела також можуть показувати абсолютний шлях. Для відображення використовуйте `filename` або метадані `relative_path` стандартного завантажувача каталогів. Перевантаження реєстрації каталогу з налаштуваннями не додає `relative_path` автоматично.

**Наявні індекси:** Старі відносні ID не видаляються й не мігрують автоматично. Бажано заново проіндексувати всі документи в новій колекції, перевірити її, а потім переключити застосунок. Якщо використовуєте стару колекцію, видаляйте лише попередні ID з перевіреною належністю та повторно індексуйте їхні вихідні файли. Не видаляйте документи масово за назвою файлу: інші каталоги можуть містити документи з такою самою назвою.

Щоб оновлення й видалення стосувалися лише потрібного документа, `document_id` зарезервовано конвеєром. Перед збереженням кожен запис отримує фактичний `RagDocument.Id`, навіть якщо вхідні метадані містять інше значення. Словники метаданих вхідного документа та розділювача не змінюються; власні обробники збереження також отримують нормалізовані записи. Для ідентифікатора застосунку використовуйте інший ключ.

Це не виправляє записи, уже збережені з неправильним `document_id`. Створіть нову колекцію з перевірених джерел або визначте належність і очистьте лише уражені записи перед переіндексацією. Повторна індексація з правильним ID сама по собі не дозволяє надійно знайти старі записи під іншим ID.

Той самий файл за відносним та абсолютним шляхом має оновлювати один документ, а однойменні файли в різних папках мають залишатися різними. `WordDocumentLoader`, `ExcelDocumentLoader`, `PowerPointDocumentLoader` і `PdfDocumentLoader` тепер записують у `DoclingDocument.Source` нормалізований абсолютний шлях, як вбудовані TXT-завантажувачі. RAG формує з нього автоматичний ID; явно задані ID залишаються під контролем викликача. Стандартні посилання на джерела можуть показувати абсолютні шляхи.

[Зберігати сталу ідентичність файлу](document-loaders.md#file-source-identity).

<a id="empty-document-updates"></a>

### Очищення документа без збереження застарілих результатів

Якщо ви очистили скасовані правила повернення коштів і повторно індексуєте той самий документ, старий текст більше не має потрапляти у відповіді. За стандартного зберігання RAG успішне розбиття з нульовою кількістю фрагментів замінює записи відповідного `document_id` порожнім набором. Ембединги не запитуються, записи інших документів зберігаються. Це стосується порожніх документів і документів із пробілів, якщо розбиття дає нуль фрагментів, а також власних роздільників, що успішно повертають нуль фрагментів.

Для вже налаштованого екземпляра `RagPipeline` з назвою `pipeline` використайте збережений ID документа:

```csharp
await pipeline.IndexDocumentAsync(
    new RagDocument { Id = "refund-policy", Content = "" },
    cancellationToken);
```

Згодом можна знову індексувати непорожній текст із тим самим ID. Відсутність документів у результаті завантажувача або відсутність документа в наступному списку файлів не є командою видалення: ID для заміни не було передано.

Винятки під час завантаження, розбору чи розбиття, а також скасування, виявлене до виклику сховища, зберігають попередні записи цього документа. Завантажувачі та парсери мають повідомляти про помилки винятками: успішний результат із нуля фрагментів неможливо відрізнити від навмисного очищення. Після початку запису відкат у разі помилки або скасування залежить від сховища; PostgreSQL виконує заміну в транзакції. Пакет обробляється окремо за документами та не відкочує вже завершені документи.

**Власне зберігання:** якщо передано `onDocumentEmbedded`, збереженням і далі керує цей callback. За нуля фрагментів він не викликається, а стандартне сховище не використовується. Застосунок має явно видалити відомий ID у власному сховищі або викликати `DeleteDocumentAsync` для сховища конвеєра.

## Власний провайдер ембеддингів

За замовчуванням RAG використовує вбудований локальний провайдер ембеддингів. Щоб використати окрему модель ембеддингів:

```csharp
using Mythosia.AI.Rag.Embeddings;

var embedder = new OpenAIEmbeddingProvider(apiKey, http, "text-embedding-3-small");

var service = new AnthropicService(apiKey, http)
    .WithRag(rag => rag
        .UseEmbedding(embedder)
        .AddDocument("knowledge-base.txt")
    );
```

## Власне векторне сховище

За замовчуванням використовується сховище в пам'яті. Для продакшену підключіть персистентне векторне сховище:

```bash
dotnet add package Mythosia.VectorDb.Postgres
```

```csharp
using Mythosia.VectorDb.Postgres;

var store = new PostgresStore(new PostgresOptions
{
    ConnectionString = connectionString,
    Dimension = 1536
});

var service = new OpenAIService(apiKey, http)
    .WithRag(rag => rag
        .UseStore(store)
        .AddDocument("large-corpus.txt")
    );
```

## Параметри запиту

Тонке налаштування поведінки витягування для кожного запиту:

```csharp
var options = new RagQueryOptions
{
    FinalFilter = new RagFilter
    {
        TopK = 5,          // кількість чанків для витягування
        MinScore = 0.7     // мінімальна оцінка схожості
    }
};

Після пошуку документів підготовка відповіді може зайняти час. [Run](execution-api-transition.md) дає змогу показувати її перебіг і скасовувати виконання, зберігаючи RAG-пошук та доповнення контексту.

var response = await service.GetCompletionAsync("Your question", options: options);
```
