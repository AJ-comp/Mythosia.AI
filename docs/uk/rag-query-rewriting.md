# Переписування запитів

> 📍 **Пайплайн запитання-відповіді:** **`Переписування запитів`** → Фільтрація → Ембеддинг (за потреби) → [Пошук](rag-hybrid-search.md) → [Переранжування](rag-reranking.md) → Побудова контексту

Етап запиту `Embedding` залежить від компонента; лексичний пошук його не повідомляє. Власний компонент може повідомляти етапи через `request.ProgressAsync`. Ембеддинги документів не змінюються.

## Навіщо потрібне переписування

У багатокроковому діалозі користувачі часто вживають займенники та короткі посилання:

> Користувач: «Розкажи про політику повернення.»
> Користувач: «А які є винятки з **неї**?»

Якщо запит «А які є винятки з неї?» надіслати у векторне сховище як є, ембеддинг не зрозуміє, до чого стосується «неї». Пошук поверне нерелевантні результати, і якість відповіді постраждає.

**Переписування запитів** розв'язує подібні посилання перед пошуком, розгортаючи «неї» → «винятки з політики повернення», щоб ембеддинг вловив повний зміст. Крім того, реалізовано механізм **шлюзу пошуку** — якщо запит не потребує звернення до бази (наприклад, «Дякую!»), пошук пропускається повністю, що заощаджує час і ресурси.

## Налаштування

`LlmQueryRewriter` використовує той самий AI-сервіс для переписування запиту перед ембеддингом:

```csharp
.WithRag(rag => rag
    .WithQueryRewriter(250)          // Використовує той самий AI-сервіс
    .AddDocument("docs.txt")
)
```

Модуль переписування аналізує контекст діалогу й формує самодостатній пошуковий запит, який векторне сховище може зрозуміти без історії бесіди.

## Багатокроковий RAG

При прямому запиті до `RagStore` передавайте історію діалогу, щоб модуль переписування зміг розв'язати посилання:

```csharp
var history = new List<ConversationTurn>
{
    new ConversationTurn("What is the refund policy?", "You can return items within 30 days."),
    new ConversationTurn("What about digital products?", "Digital products are non-refundable.")
};

var result = await store.QueryAsync(
    query: "Are there any exceptions to that?",
    conversationHistory: history
);
```

Модуль бачить повну історію і переписує «Are there any exceptions to that?» у щось на кшталт «exceptions to the digital product non-refundable policy», що значно покращує результати пошуку.

## Зміна переписування під час обробки запитів

> Щоб зміна переписувача під час роботи поширювалася на наявні обгортки `WithRag(store)`, потрібен `Mythosia.AI.Rag` 8.1.1 або новіший. [Примітки до виправлення](../../src/rag/Mythosia.AI.Rag/RELEASE_NOTES.md#v811).

Щоб додати або замінити переписувач без перебудови індексу, використовуйте `store.SetQueryRewriter(rewriter)`; `store.SetQueryRewriter(null)` вимикає переписування й виділення пошукових слів. І перевантаження `RagStore.QueryAsync`, що приймає `conversationHistory`, і вже під’єднані через `service.WithRag(store)` обгортки вибирають поточний переписувач сховища для кожного запиту. Запит зберігає вибраний екземпляр під час очікування повідомлення про перебіг виконання чи переписування. Додавання, заміна або вимкнення діє на наступні запити, зокрема пошук, створення відповідей, потокові відповіді та Run через ці обгортки.

```csharp
var rag = service.WithRag(store);
store.SetQueryRewriter(rewriter);
var rewritten = await rag.RetrieveAsync("Які винятки є в правилах повернення коштів?");

store.SetQueryRewriter(null);
var original = await rag.RetrieveAsync("Які винятки є в правилах повернення коштів?");
```

Стандартний `LlmQueryRewriter`, увімкнений через `WithQueryRewriter()`, створюється один раз під час відкладеної ініціалізації; після вимкнення він не створюється знову з наступним запитом. Перевантаження сховища без `conversationHistory` і надалі оминають переписування. Це стосується й агентного RAG, де пошуковий запит формулює сам агент.

## Як працює шлюз пошуку

Не кожне повідомлення користувача потребує звернення до документів. Модуль переписування класифікує запит і повертає порожній результат для повідомлень на кшталт:

- «Дякую!»
- «Зрозумів, це корисно.»
- «Можеш підсумувати те, що щойно сказав?»

Коли шлюз спрацьовує, весь пайплайн витягування пропускається — ні ембеддингу, ні векторного пошуку, ні переранжування — і LLM відповідає безпосередньо з контексту діалогу.
